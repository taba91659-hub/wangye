# 聊天内新增账单

已实现独立 add_expense 写工具；本地测试不代表线上部署或确认按钮已验收。只改新增，删除仍经本人网页确认。

## 部署
1. 上传本包到仓库根目录，新分支 ledger-chat-add，PR核对后合并。
2. Supabase SQL编辑器运行11-chat-add-expense.sql全文，默认关闭新能力。不要重跑旧迁移。
3. 用本包supabase/functions/ledger-mcp/index.ts全文更新函数并Deploy updates。Legacy JWT验证保持关闭，OAuth配置不变。
4. ChatGPT应用管理页刷新工具，确认出现add_expense；这是会真正保存的写操作。
5. 在应用权限中选择每次写操作询问（若当前界面提供）。确认按钮受ChatGPT设置和客户端行为控制，代码无法保证每次弹出。不要把annotations或模型传入confirmed=true当作用户确认凭证。本方案由客户端负责确认；服务器验证账号、客户端、参数与重复请求，不验证点击收据。
6. 执行12-enable-chat-add.sql，enabled/drafts_enabled/chat_add_enabled均为true。
7. 用一笔真实要记录的支出验收：ChatGPT展示名称、金额、分类、日期，在聊天内请求写操作确认；本人确认后保存，原App恰好增加一笔，无需打开网页。若没有达到每次确认的效果，执行13-disable-chat-add.sql停用此新路径，继续使用已有网页草稿，反馈实际界面后再处理。不要把默认自动批准称为满足本次需求。

## 行为
普通记账优先调用add_expense；不要先调用prepare_expense制造两次写操作确认。只有用户主动要网页方式才用旧草稿工具。
同一意图必须沿用request_id重试；改编号会视为新账单。字段变化需用户确认新内容和新意图。同一请求已保存但账单后来被删除时，返回currently_exists=false，不会自动重建。
仅status=saved且currently_exists=true可宣称账单现在存在。网络失败需沿用原编号核对，不能盲目换号重记。
关闭chat_add_enabled不影响原查询、新增网页确认和删除流程。后端仍禁止OAuth直接增删改原表，只开放绑定账号和客户端的固定用途RPC。
